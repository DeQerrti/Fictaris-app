# Скрипторий (Scriptorium)

Инструмент для писателей и мастеров подземелий — альтернатива Obsidian, специализированная под worldbuilding и художественное письмо: персонажи, локации, фракции, связи, таймлайн, интерактивная карта, канбан-доска и текстовый редактор в одном приложении.

> **Как читать этот документ.** Это склейка двух источников: (1) полный бриф, написанный в другом чате, и (2) факт-чек и дополнения из чата, где реально писался код. Второй чат работал итеративно — пользователь присылал "продолжай" / скриншот роадмапа, а Claude сам решал, что делать дальше, писал код и заливал файл. Раздел «Реальный статус реализации» ниже — самое важное: часть функций из полного списка ниже была только спроектирована на бумаге в обсуждении, часть — реально закодирована и провалидирована, а часть — начата, но не доведена до конца в момент, когда сессия прервалась. Не считайте весь список ниже кодом, который уже существует и работает.

## Контекст и мотивация

Отправная точка — человек искал приложение уровня Obsidian, но заточенное именно под писателей и DM: с карточками персонажей, интерактивной доской, таймлайном, картой. Сравнили существующие решения — ни одно не устроило по совокупности цены/функций/приватности, решили строить своё.

**Конкурентный анализ** (проводился в одной из сессий): сравнивали против World Anvil, LegendKeeper, Campfire, Obsidian+плагины и отдельно против инструмента **e-writer**. По итогам сравнения с e-writer выделили три приоритета для роадмапа, которые ещё не реализованы ни в коде, ни в дизайне: **экспорт в `.docx`**, **поддержка нескольких проектов в рамках одного хранилища** (сейчас приложение жёстко рассчитано на один "мир"/рукопись за раз), и **инлайн-комментарии, привязанные к выделению текста** в редакторе главы (не путать с «заметками автора» — те на уровне главы целиком, а не на конкретный фрагмент).

**Ключевой нерешённый вопрос платформы:** сейчас приложение — React PWA-артефакт, работающее в браузерном интерфейсе Claude, с хранением через `window.storage` (простое key-value хранилище). Это **не то же самое**, что модель Obsidian (файлы на диске). У `window.storage` жёсткий лимит **5MB на ключ** — экспериментально проверено (см. раздел «Проверенные технические риски»), что при активном использовании (много персонажей с фото-референсами) это реально исчерпывается. Именно поэтому запускается миграция в Claude Code — там можно сделать нормальное Electron/Tauri приложение с хранением на файловой системе, без этого потолка.

## Рабочий процесс, который стоит воспроизвести в Claude Code

Этот паттерн работал хорошо и стоит сохранить в новом чате:
- Пользователь присылал короткий стимул — слово «Продолжай» или скриншот сгруппированного по смыслу списка идей — без детальной спецификации.
- Приоритизацию и разбивку на подзадачи Claude брал на себя: сам решал, какие 3–5 пунктов реализовать за один проход, не спрашивая лишний раз.
- Каждый проход — это: прочитать текущий файл целиком → внести точечные правки (`str_replace`, а не переписывание с нуля) → **обязательно прогнать через `esbuild` для проверки синтаксиса JSX** до того, как отдавать файл пользователю → выдать обновлённый файл.
- Правки шли пачками, сгруппированными по смысловому блоку (например: всё «Рукопись» за один проход, затем «Сущности и связи» за другой), а не по одной функции за раз.
- В конце ответа — короткий отчёт, что именно сделано, и честный список того, что **осознанно оставлено на потом** (не выдавать желаемое за сделанное).

## Технологический стек (текущая версия, для референса)

- React (функциональные компоненты, hooks: useState/useEffect/useRef/useMemo)
- Tailwind (только core utility-классы + произвольные значения `bg-[#hex]`)
- lucide-react для иконок
- Хранение: `window.storage.get/set` (JSON.stringify/parse), с debounce-сохранением (600мс) и индикатором статуса «Сохранение…/Сохранено»
- Изображения: `<canvas>` для сжатия загружаемых файлов (масштаб + JPEG quality) перед сохранением как base64 dataURL
- Один большой файл-компонент (`scriptorium.jsx`), без сборочного пайплайна на стороне пользователя — весь код в одном месте

## Технические детали, которые важно не потерять

1. **Автолинк `@упоминаний` — баг с кириллицей**: `\b` в JS-регулярках не распознаёт кириллические буквы как word characters (это чисто ASCII-концепция), поэтому границы совпадений ломались. Исправлено через negative lookahead: `` `@(${names})(?![A-Za-zА-Яа-яЁё0-9_])` `` вместо `\b`.
2. **Таймлайн: сортировка через fractional order** — при drag-and-drop новый `order` вычисляется как среднее между соседями (`(prev.order + next.order) / 2`), а не через полную перенумерацию — это позволяет автоматической сортировке по дате и ручному drag сосуществовать без конфликтов.
3. **Вложенные карты** — рекурсивное удаление через `collectMapIds()` (обходит дерево пинов, собирает все id под-карт, которые нужно удалить вместе с родительской меткой-порталом).
4. **Компоненты переиспользуются между сущностями за счёт одинаковой формы объекта**: `CharacterChips` и `CharacterSelect` принимают любой массив с полями `{id, name, color}`, поэтому их же используют для выбора/отображения локаций — не переименовывая и не дублируя компонент. Полезный паттерн при добавлении фракций и нитей сюжета в будущем.
5. **Проверка синтаксиса перед выдачей файла**: в среде с bash-доступом рабочий цикл включал `npx esbuild scriptorium.jsx --bundle --loader:.jsx=jsx --outfile=/tmp/out.js --external:react --external:lucide-react` как быстрый синтаксис-чек JSX до того, как файл уходит пользователю. В Claude Code эквивалент — обычный запуск сборки/тайпчека проекта.

## Проверенные технические риски (эмпирически протестировано в одной из сессий)

Сгенерировали тестовые изображения через Pillow с теми же параметрами, что задаёт `compressImage()` (maxWidth + JPEG quality), измерили реальный вес base64:

| Сценарий | Вес/единица | Лимит 5MB на ключ исчерпается на |
|---|---|---|
| Персонаж, 6 фото-референсов (пример: реальные фото) | ~1.1 MB | 4–5-м персонаже |
| Персонаж, 6 иллюстраций (цифровой арт) | ~480 KB | 10–11-м персонаже |
| Персонаж, 2 фото-референса | ~360 KB | 14–15-м персонаже |
| Персонаж, 2 иллюстрации | ~160 KB | 32–33-м персонаже |
| Детально прорисованная под-карта | ~300 KB | 17–18-й карте |

**Вывод**: проблема архитектурная — все персонажи хранятся одним JSON-блобом под один ключ `scriptorium:characters`, поэтому лимит общий на весь ростер, а не на персонажа. При переносе на файловую систему (Electron/Claude Code) этот потолок исчезает полностью, но если по какой-то причине останется key-value подход — правильное решение: разносить изображения по отдельным записям на сущность, а не бандлить в общий массив.

## Что стоит сохранить в новой версии (Claude Code / Electron)

- Модель данных и функциональность как описано выше — она продумана и большей частью проверена в UI, менять не за чем, но **сверяйтесь с реальным кодом**, а не только с этим брифом, если он есть под рукой
- Дизайн-систему (цвета/шрифты/паттерны) — узнаваемый и atmospheric визуальный язык
- Автосохранение с debounce + видимый статус — привычный UX, который стоит сохранить
- Паттерн переиспользуемых chips/select-компонентов через одинаковую форму объекта (см. технические детали, п.4)
- Рабочий процесс: короткие стимулы от пользователя → Claude сам приоритизирует и группирует правки → синтаксис-чек перед выдачей → честный отчёт о том, что сделано и что осознанно отложено

## Что стоит пересмотреть при переносе

- **Хранение** — файлы на диске вместо `window.storage`; вероятно, один файл проекта (по аналогии с Obsidian vault) или папка с отдельными файлами по сущностям
- **Изображения** — хранить как отдельные файлы на диске (не base64 в JSON), это разом снимает и лимит размера, и раздувание основного файла проекта
- **Формат хранения** — раз уж уходим от JSON-блоба, возможно, стоит рассмотреть markdown+frontmatter по сущности (ближе к духу Obsidian, человекочитаемо, компонуется с git для версионирования) — решение ещё не выбрано окончательно
- **Многопроектность** — раз это один из трёх приоритетов роадмапа, продумать структуру хранения сразу под несколько "миров"/рукописей, а не добавлять поверх однопроектной модели задним числом
